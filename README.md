# طلبات شراء محل كنوز البلد

صفحة ويب عربية متجاوبة للموبايل، وليست تطبيق Android أصلياً. نموذج أولي وظيفي يحتاج إعداد Firebase واختباراً عملياً قبل الاستخدام التجاري.

## الميزات
- بطاقات متعددة بعناوين، ومواد مرقمة داخل كل بطاقة.
- اسم وكمية نصية مع وحدة وملاحظات وملاحظة صوتية حتى 15 ثانية.
- تحديد الشراء يخفي المادة من النواقص؛ سجل المشتريات يسمح بإعادتها.
- وضع محلي على المتصفح، أو مشاركة فورية عبر Firebase Firestore بعد الإعداد.
- لا ترفع البيانات المحلية إلى قاعدة البيانات تلقائياً عند الاتصال.

## التشغيل والرفع على GitHub
1. أنشئ مستودعاً في حسابك باسم konouz-purchases. لا ترفع كلمات مرور أو ملفات مفاتيح حساب الخدمة.
2. ارفع index.html إلى جذر المستودع باستخدام Add file > Upload files ثم Commit changes. يمكن رفع README.md وfirestore.rules أيضاً.
3. من Settings > Pages اختر النشر من فرع main والمجلد الجذر ثم احفظ. قد تختلف مسميات الواجهة.
4. افتح عنوان GitHub Pages الذي يظهر لك بعد اكتمال النشر. الصفحة نفسها لا تحتاج عملية build.
5. استخدم HTTPS للتسجيل الصوتي، وامنح إذن الميكروفون. لا تعتمد على فتح الملف مباشرة كطريقة تشغيل نهائية.

## تفعيل تعدد المستخدمين
1. أنشئ مشروع Firebase ثم سجّل Web app وانسخ firebaseConfig.
2. فعّل Authentication > Email/Password، وأنشئ حسابات الموظفين من لوحة الإدارة. الصفحة لا تتضمن واجهة إنشاء حساب.
3. أنشئ Cloud Firestore، ولا تستخدم قواعد الاختبار المفتوحة.
4. انسخ UID لكل موظف من Authentication وضعه بدلاً من القيم الوهمية في firestore.rules. أضف جميع الموظفين المسموح لهم في القائمة.
5. انشر القواعد من تبويب Rules في Firestore. الإذن مقتصر على المحل konouz-albalad. إذا غيرت معرف المحل فعليك تغيير القواعد أيضاً. لا تمنح الوصول لجميع الحسابات دون قائمة سماح.
6. أضف نطاق GitHub Pages إلى Authorized domains في إعدادات Authentication عند الحاجة.
7. في الصفحة افتح إعداد المشاركة، والصق الإعدادات كـ JSON صحيح بأسماء خصائص بين علامات اقتباس مزدوجة، دون const أو تعليقات أو فاصلة أخيرة. احتفظ بالمعرّف konouz-albalad.
8. سجّل دخول الموظف. يكرر كل موظف الإعداد نفسه على جهازه مع حسابه الشخصي. لا تظهر المواد إلا بعد نجاح قراءة قاعدة البيانات.

مثال الإعدادات (استبدل القيم):
```json
{"apiKey":"YOUR_WEB_API_KEY","authDomain":"YOUR_PROJECT.firebaseapp.com","projectId":"YOUR_PROJECT","appId":"YOUR_APP_ID"}
```
إعدادات تطبيق الويب عامة وليست بديلاً عن قواعد الأمان. لا تلصق service-account أو private_key. الدخول وحده لا يكفي: UID يجب أن يكون ضمن قائمة القواعد.

## اختبار القبول
- من جهازين وحسابين مصرح بهما: أنشئ بطاقة ومادة من الأول وتحقق من ظهورهما في الثاني.
- علّم المادة مشتراة؛ يجب أن تختفي من النواقص في الجهازين، ثم أعدها من سجل المشتريات.
- سجّل ملاحظة صوتية واحفظ المادة واختبر تشغيلها على الجهاز الآخر.
- جرّب حساباً خارج قائمة UID وتأكد من رفض الوصول، وجرّب المتصفح على شاشة موبايل.

## حدود مهمة
- لم يُختبر المشروع في متصفح حقيقي أو مشروع Firebase فعلي أثناء توليده. يجب إجراء الاختبارات أعلاه.
- الوضع المحلي ليس متعدد المستخدمين، وقد تضيع بياناته عند مسح بيانات المتصفح أو تجاوز سعة التخزين. ملفات الصوت تستهلك السعة سريعاً.
- الملاحظات الصوتية مخزنة داخل مستند المادة بصيغة base64؛ الحد 350 كيلوبايت للتسجيل قبل الترميز. التسجيل الأكبر يُرفض. للإنتاج الكثيف يفضل مخزن ملفات مع قواعد صلاحيات منفصلة.
- جميع الموظفين المسموح لهم يقرؤون ويعدلون بطاقات المحل؛ لا توجد أدوار إدارية داخل الواجهة أو حذف نهائي أو نسخ احتياطي مدمج.
- تحتاج المشاركة اتصال إنترنت. لا يوجد service worker أو ضمان عمل مشترك دون اتصال. اتصالان متزامنان على حالة شراء المادة يخضعان لآخر تحديث يصل للخادم.
- تعتمد الصفحة على تحميل Firebase SDK من شبكة خارجية. تحقق من توفر Firebase في شبكتك ومن متطلبات الفوترة والحدود قبل الاعتماد التجاري.
- لا يوجد ترحيل تلقائي من البيانات المحلية، ولا تصدير مدمج، ولا تشفير طرفي للملاحظات.
- لم يتم رفع المشروع إلى GitHub من هذه المحادثة، ولم يتم إنشاء مشروع Firebase أو حسابات مستخدمين.
